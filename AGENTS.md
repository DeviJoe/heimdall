# LinPam - система привелигированного доступа на сервера с Linux

Это система, задача которой - обеспечивать синхронизацию параметров учетных
записей пользователей на Linux сервера. Архитектура - клиент-серверная.
Присутствует разделение на control plane, web интерфейс и агенты, работающие
на нодах Linux. Язык реализации backend - Go, реализация фронта - React.
В качестве БД используется PostgreSQL, для хранения кэша сессии - Redis.
Для тестирования разработки и локального развертывания
на одной ноде используется Docker и Docker Compose.

Стиль UI/UX - material design 3.

Что должна хранить система? В целом, по user experience это должно быть
похоже на LDAP. Система хранит внутри себя список пользователей,
может присутствовать интеграция с провайдерами OIDC и LDAP для поставки
пользователей, должна быть поддержка локальных пользователей. Каждый пользователь
логинится по Login, Password. Должна быть возможность при локальных УЗ
при заведении пользователя генерировать ему ссылку для первого входа,
где он сможет задать для входа пароль. Должна быть возможность включить
регистрацию второго фактора: TOTP или Passwordless на УЗ, должна быть возможность
при регистрации пользователя сделать привязку обязательной, иначе он не сможет пользоваться
системой.

Для каждого пользователя должны задаваться те же параметры, что и для
LDAP (uid, gid, homedir, login shell, gecos, user password).
Все поля должны быть автоматически вычисляемы, но при этом их можно было бы
поменять. Важно, что задавание пароля точно не должно быть обязательным, опциональным,
пароль само собой не хранится, только хэш пароля в БД.
Каждый пользователь сможет привязывать к своей УЗ 1 или несколько SSH ключей, должна
быть возможность сгенерировать такой ключ из интерфейса. Должна быть возможность у администратора
запрещать ключи, если они не поддерживают sk - то есть без passwordless ключа.
Ну и генерировать такой тип ключей тоже было бы хорошо из интерфейса, если можно.

Далее, ключами нужно уметь управлять в своей УЗ, удалять, добавлять, называть. У клюей должен быть срок жизни,
задаваемый администратором. Если срок истекает, ключ блокируется, его нельзя использовать повторно, удаляется, но повторно его добавить уже нельзя будет.

Все ключи и параметры должны синхронизироваться с подключенными машинами. Машины подключаются по Join токенам. далее они вырабатывают с conrol plane сертфиикаты и далее работают и ротируют уже их. На нодах должен работать агент в фоне, который и будет обеспечивать синхронмзацию
Подключенные машины должны по gprc поднимать тунель до управляющей плоскости, и по ней получать данные о новых ключах и изменениях.
Важно, если даже что-то произойдет с control plane, то машины должны легковесно подключаться к нему и не уложить его ddos-ом, как например, делал Teleport.
Любые изменения у пользователей должны приводить к изменениям параметров из УЗ на машинах. Также важно, что это решение должно имеено создавать УЗ, копировать ключи, то есть упрвлять реальными Linux пользователями на машинах.

Все подключенные сервера должны отображаться в админ-панели, должен быть heartbit, должно показываться, какие сервера не обновлялись, с какими все хорошо, какие потерялись и не вернулись.

Должна быть ролевая модель, должна быть возможность доставлять для пользователей их Sudoers права, но настраивать их должны администраторы, а не пользователи, также должна быть ролевая модель для управления пользователями, администраторами, серверами, судоерс правами, сервера надо уметь объединять в группы и по разному применять права для этих групп. Возьми RBAC как модель реализации ролевой модели

Следи за сложностью алгоритмов, не надо делать высокую сложность вычислительную, программа должна работать быстро и выдерживать масштабирование, она должна держать хотя бы 20 тысяч подключенных агентов, иметь возможность расширяться.

Соблюдай чистоту структуры, руководствуйся DDD, Clean code и best practice по Go и React JS. Правильно разбивай все по папкам, не делай лишних README и инструкций

У control plane должен быть сервер метрик, его должна быть возможность закрыть за mtls и password

Параметры настройки Control Plane должны быть вынесены в YAML, пароли от БД и прочая секретная информация должна иметь возможность задаваться через переменные окружения
