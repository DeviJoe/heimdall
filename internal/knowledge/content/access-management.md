# Управление доступом и граф назначений

## Объекты доступа

| Раздел | Назначение |
| --- | --- |
| Пользователи | Учётка Heimdall, UNIX-профиль, состояние, синхронизация на ОС |
| Группы людей | Команды, права управления Heimdall и требования TOTP/Passkey/SK |
| UNIX-каталог | Primary GID и supplementary POSIX-группы |
| Доступ → Роли | Права Heimdall либо способы UNIX-входа и sudo |
| Доступ → Назначения на ноды | UNIX-группа → роль входа/sudo → группа нод |
| Ноды | Хосты, группы хостов, hostname/IP и подтверждение синхронизации |

Группа людей и UNIX-группа — разные объекты. Группа людей не создаёт одноимённую группу на ОС. UNIX-назначение не выдаёт права администрирования Heimdall, даже если они записаны в используемой роли.

## Выдать доступ инженеру

1. Создайте пользователя и передайте приглашение для первого входа. Пароль Heimdall не является UNIX-паролем.
2. В профиле пользователя включите **Синхронизировать UNIX-учётку**. Для администратора продукта это обычно не нужно.
3. В **UNIX-каталоге** создайте группу или выберите существующую. Добавьте supplementary участников; primary группу задаёт GID профиля.
4. В **Доступ → Роли** создайте роль с назначением **Вход на ноды и sudo**. Явно разрешите SSH-ключи и/или UNIX-пароль. По умолчанию оба способа запрещены.
5. Если нужен sudo, настройте конструктором либо нативным текстом правую часть User_Spec. Вкладка текста показывает результат. Агент проверяет конфигурацию через `visudo`.
6. Откройте **Доступ → Назначения на ноды**, нажмите **Назначить доступ** и выберите UNIX-группу, роль и группу нод. Дочерние группы нод наследуют назначение.
7. Пользователь подключает SSH-ключ и требуемые факторы в своём профиле. Для парольного UNIX-входа отдельно задаётся UNIX-пароль, если он разрешён ролью.
8. Дождитесь зелёного состояния ноды и подтверждения операции. Пользователь увидит доступные хосты в разделе **Ноды**, а свои методы, ключи и факторы — в профиле по аватару.

Нет назначения, выключена синхронизация, пользователь заблокирован, не выполнены факторы/мандатные требования или не разрешён ни один метод — доступ запрещён. Назначения складываются: удаление одной роли не отменяет разрешение, которое выдаётся другой ролью.

Оператор с `users.manage` не может обойти управление ролями изменением UNIX-членства или primary GID. Для привилегированной группы дополнительно нужны `roles.manage` на её областях и `sudo.manage`, если выдаётся sudo.

## Права управления Heimdall

Создавайте роли с назначением **Управление Heimdall** и необходимыми permissions, затем назначайте их группе людей на нужной области. `*` в области означает глобальное назначение; `*` в permissions означает все административные права. Персональные назначения в профиле используются как явные исключения. Роли с правами управления сами по себе не разрешают SSH.

Изменения групп с ролями проверяют право делегировать соответствующие permissions. **Совмещённая роль** позволяет настроить обе части, но для понятной модели предпочтительны отдельные роли управления и входа на ОС. Переключение назначения на одну часть удаляет другую из редактируемой формы; изменения применяются только после подтверждённого сохранения. Последний активный глобальный администратор защищён от удаления прав/блокировки, в том числе при снятии персонального или группового назначения. Снять собственное назначение можно, если остаётся другой действующий администратор. Для выдачи и отзыва роли с sudo, а также изменения или удаления её sudoers требуется `sudo.manage`. Опасные изменения требуют подтверждения последствий.

Для оператора назначения на определённую группу нод: предоставьте `roles.manage` на этой области, глобальное чтение каталога `roles.read` и `users.read`/`users.manage` для UNIX-групп. Для sudo добавьте `sudo.manage` на той же области. Глобальные права создания определений ролей при этом не требуются. Видимые области наследуются от родительской группы нод; другие назначения оператору недоступны.

## Факторы и мандатные ограничения

Администратор задаёт минимум TOTP, Passkey, любой фактор, оба или опционально для пользователя/группы людей. Пользователь может подключить дополнительные факторы и усилить личные требования. Ослабить административный минимум нельзя. При смене TOTP старый остаётся рабочим до проверки нового QR/кода. Администратор может отозвать фактор для повторной регистрации; требования сохраняются.

Метки пользователя должны доминировать над уровнем и категориями группы нод с учётом наследования. Это дополнительное ограничение к RBAC, не самостоятельная выдача доступа.

## Отозвать доступ

Заблокируйте пользователя либо отзовите последнее разрешение на целевую группу нод. Выключение синхронизации UNIX-учётки тоже отзывает ранее доставленный доступ.

После получения подписанного состояния агент блокирует вход, удаляет ключи, пароль, sudo и supplementary членство, затем завершает SSH-соединения, `tmux`/`screen`, `nohup` и остальные процессы пользователя, включая найденных дочерних процессов sudo. Агент подтверждает применение только после завершения операции. Неполное завершение видно как ошибка синхронизации; журнал позволяет повторить действие после перезапуска агента. Домашний каталог не удаляется.

Если нода offline, отзыв остаётся неподтверждённым, отображается инцидент. Недоступность control plane/агента сама по себе не блокирует учётки и не завершает процессы. Отключение управления нодой (`disabled`) сохраняет её локальное состояние; это не способ отозвать доступ.

Удаление отдельного ключа или части sudo не завершает все процессы автоматически, если у пользователя остаётся разрешённый доступ. Для полного прекращения работы выполните полный отзыв.

## Изучить граф

Откройте **Доступ → Граф доступов**. Ссылка открывает отдельную вкладку. Граф состоит из трёх колонок: **Кому → Что разрешено → Где**. Одинаковая роль в разных областях показана разными узлами назначения: связь не означает доступ ко всем областям, где встречается название роли.

- Ищите по субъекту, роли и группе нод. Фильтр источника различает UNIX-группы, группы людей и персональные исключения.
- Списки и граф используют серверную пагинацию; выбирайте 10/25/50/100 назначений на странице. Запросы выполняются при открытии/смене фильтра/страницы.
- Перетаскивайте пустой фон, используйте масштаб +/−, **Вместить** и **Сбросить**. Клавиатура: +/−, стрелки, Enter на узле, Escape снимает выделение.
- Нажмите узел для просмотра цепочки, методов, permissions и sudoers. **Показать связи** у рекомендации выделяет относящиеся назначения.
- Рекомендации находят одинаковые определения ролей и общие права одного субъекта на совпадающих/наследуемых областях. Они не изменяют данные автоматически.

Анализ ограничен текущей страницей и не анализирует произвольные пересечения sudoers-шаблонов, членство разных групп, факторы и текущий статус доставки. Граф показывает конфигурацию, а эффективный доступ конкретного человека смотрите в его профиле. Для доступа к графу нужны глобальные `roles.read`, `users.read` и `nodes.read`.
