# Роли и группы

Основной способ предоставить доступ:

**UNIX-группа → группа нод → UNIX-роль.**

Например: UNIX-группа `platform` получает роль `Operator` на группе нод `Stage`. Только участники `platform`, для которых включена синхронизация, получают эту роль на нодах `Stage` и её дочерних групп. Без назначения доступ запрещён.

## Три разных каталога

- **Пользователи** — учётные записи людей и сервисов в Heimdall. У человека есть пароль веб-входа и факторы. Сервисная учётка не входит в веб-интерфейс.
- **Группы людей** — команды и политики факторов Heimdall. Можно переносить пользователей между группами. Требования нескольких групп складываются: более слабая группа не отменяет TOTP, обязательный в другой.
- **UNIX-каталог** — реальные POSIX-группы с GID, primary и supplementary membership. Здесь назначают доступ к группам нод.
- **Группы нод** — иерархия серверов. Это область применения назначения, а не UNIX-группа.

## Назначить доступ

1. В **Пользователи → профиль** включите «Синхронизировать UNIX-учётку на ноды». Для администратора, которому нужен только веб-интерфейс, оставьте выключенным.
2. В **UNIX-каталог** создайте группу с POSIX-именем и GID, добавьте участников.
3. В **Роли → Вход на ноды** создайте роль, явно включите SSH-ключи и/или парольный вход; при необходимости задайте sudoers.
4. В **UNIX-каталог → Назначения** выберите UNIX-группу, группу нод и роль.
5. Дождитесь подтверждения агентов в разделе **Синхронизация**.

Несколько назначений объединяют разрешённые методы и sudoers. Отдельных правил «deny» в ролях нет: запрет достигается отсутствием разрешения; отключение синхронизации, блокировка пользователя, невыполненная политика факторов и мандатные метки ограничивают все назначения.

## Права в Heimdall

Вкладка **Права Heimdall** управляет API и административными действиями: пользователи, ноды, роли, аудит, настройки. Эти права не создают UNIX-учётку. `*` означает все административные права. Токен дополнительно ограничен собственными scopes, группами и audience; он не расширяет права владельца.

Прямые назначения в профиле и назначения через группы людей поддерживаются для исключений и административных обязанностей. Для массового UNIX-доступа используйте единую цепочку UNIX-группа → группа нод → роль. У смешанной роли показываются обе части, чтобы права не были скрыты.

## sudoers

В редакторе доступны конструктор, исходный текст и просмотр. Текст каждой строки — правая часть стандартного User_Spec после имени пользователя:

```sudoers
ALL=(root:root) NOPASSWD: /usr/bin/id, /usr/bin/whoami
```

Агент подставляет имя конкретного пользователя, проверяет набор файлов через `visudo` и устанавливает файл с правами 0440. Не используйте `ALL` вместо команды без осознанной необходимости. Для `PASSWD` пользователю нужен отдельный UNIX-пароль и явное разрешение парольного входа; пароль Heimdall для sudo не подходит.

## Допуски и метки

Уровень допуска пользователя должен быть не ниже уровня группы нод, а его категории должны включать категории ноды. Метки только ограничивают RBAC: они не предоставляют доступ без назначения роли. Подтверждение агента нужно и для отзыва допуска.

## Удаление

Удаление роли отзывает все её назначения. Группа с дочерними группами, участниками, нодами или назначениями требует сначала убрать зависимости. Интерфейс показывает ошибку; данные не исчезают молча. Последнего активного глобального администратора удалить нельзя.
