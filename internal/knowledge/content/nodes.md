# Подключение нод

Откройте **Ноды → Управление → Токены присоединения**. Истёкшие по времени токены удаляются автоматически; уже подключённые ноды продолжают работать по сертификатам. Администратор создаёт join-токен для группы нод. Количество подключений и TTL задаются независимо: например, неограниченно в течение `365d`, либо 20 подключений в течение `7d`. Выданный секрет показывается один раз. Храните его как credential; после регистрации агент использует собственный mTLS-сертификат.

Установите подходящий бинарник `heimdall-agent`, конфигурацию и доверенный ключ подписи. Примеры конфигурации находятся в репозитории: `config/agent.yaml`; Linux systemd и FreeBSD rc.d — в `deployments`. Секреты передавайте через переменные окружения согласно именам в конфигурации.

Агент подключается к gRPC endpoint, сообщает hostname, IP и платформу. В карточке ноды можно задать адрес/порт SSH и группу. При изменении группы предыдущий доступ отзывается, новый рассчитывается заново.

## Linux и FreeBSD

ОС-пользователями управляет root-супервизор `heimdall-agent`: Linux использует стандартные инструменты shadow, FreeBSD — `pw`. SSH обслуживает системный OpenSSH. Для FreeBSD установите `sudo` и нужный shell; доступен `/bin/sh`, Bash должен быть установлен отдельно. GID, UID и домашний каталог должны принадлежать управляемой области. Чужие локальные учётки автоматически не захватываются.

## OpenSSH

Агент создаёт `/etc/heimdall/sshd_config` (или сохраняет совместимый `/etc/linpam` на старой ноде) и подключает его после глобальных настроек, до существующих Match-блоков. Внешний Include с Match-блоками до политики требует переноса ниже управляемого Include; агент сообщит ошибку. Кандидат проверяется `sshd -t`, затем демон перечитывает конфигурацию через SIGHUP. Требуется корректный абсолютный PidFile.

Правила относятся только к управляемым пользователям: разрешённые методы, root-owned authorized_keys, отключение сторонних AuthorizedKeysCommand и CA. Доступ не зависит от работы агента. При ошибке конфигурации ревизия не подтверждается; администратор видит ошибку синхронизации.

## Диагностика

В списке одно состояние: **зелёное** — синхронизировано и агент на связи; **жёлтое** — потеря синхронизации, ошибка применения или пропуск heartbeat; **красное** — offline либо отключено. Над списком есть счётчики и фильтры по состоянию, ОС и группе. Ошибка применения видна в карточке. Результаты применения и переходы состояния автоматически обновляют открытую страницу по SSE; постоянного опроса каталога нет. UUID остаётся идентификатором API, в интерфейсе используется имя ноды. Для перерегистрации утраченной ноды нужен отдельный recovery-токен администратора; нельзя обойти проверку идентичности обычным join-токеном.

## Один бинарник агента

Устанавливается один `heimdall-agent`, запускаемый root. Он сам запускает сетевой процесс под выделенной системной учёткой `heimdall-agent`; root-супервизор проверяет подписи и применяет ОС-ресурсы. Отдельный `heimdall-helper` для нового развёртывания не требуется. Сервисная учётка должна существовать до запуска.

Настройки читаются в порядке **YAML → ENV → CLI**. Например:

```sh
export HEIMDALL_JOIN_TOKEN=your-join-token
sudo --preserve-env=HEIMDALL_JOIN_TOKEN heimdall-agent -config /etc/heimdall/agent.yaml
```

YAML использует `api`, `grpc`, `server_name`, `name`, `ca_file`, `state_key`, `state_dir`, `worker_state_dir`, `socket`, `auth_log`, `run_as`, `heartbeat`. ENV: `HEIMDALL_AGENT_API`, `HEIMDALL_AGENT_GRPC`, `HEIMDALL_AGENT_SERVER_NAME`, `HEIMDALL_AGENT_NAME`, `HEIMDALL_AGENT_CA`, `HEIMDALL_AGENT_STATE_KEY`, `HEIMDALL_AGENT_STATE_DIR`, `HEIMDALL_AGENT_WORKER_STATE_DIR`, `HEIMDALL_AGENT_SOCKET`, `HEIMDALL_AGENT_AUTH_LOG`, `HEIMDALL_AGENT_RUN_AS`, `HEIMDALL_AGENT_HEARTBEAT`. Токен предпочтительно передавать через `HEIMDALL_JOIN_TOKEN`; для первоначального подключения допускается `join_token` в root-owned YAML с mode 0600.

После подключения токен можно удалить из конфигурации. Не удаляйте каталоги состояния при обновлении. Потеря агента не останавливает системный SSH и не очищает уже применённый доступ.

## Срок жизни и перевыпуск сертификатов

В **Настройки → Срок жизни сертификатов нод** по умолчанию задано **3650d — 10 лет**. Можно задать срок от 1 до 3650 дней. Это транспортный mTLS-сертификат агента; срок пользовательских SSH-ключей задаётся отдельно.

Смена срока требует подтверждения и запускает перевыпуск на всех управляемых нодах. Агент получает подписанную политику, сохраняет запрос, выпускает новый сертификат и переподключается. Счётчик **Сертификаты нод: актуальны N из M** изменяется только после подключения с новым сертификатом. Сам по себе ответ сервера о выдаче ещё не подтверждает установку. Offline-ноды остаются ожидающими; после возвращения они получают новую политику.

Карточка ноды показывает срок и состояние сертификата: актуальный, ожидает перевыпуска или истёк. Зависший перевыпуск виден как инцидент синхронизации, в метриках и Grafana. Штатная ротация распределяется между нодами и начинается за 7–8 часов до истечения.

Если сертификат уже истёк, администратор с `nodes.manage` выпускает recovery-токен для этой ноды. Токен действует 10 минут и используется один раз:

```sh
export HEIMDALL_RECOVERY_TOKEN='полученный-токен'
heimdall-agent -config /etc/heimdall/agent.yaml -recover
unset HEIMDALL_RECOVERY_TOKEN
```

Запускайте команду на целевой ноде с доступом к network state агента. Для FreeBSD используйте путь `/usr/local/etc/heimdall/agent.yaml`. Конфигурация и каталоги состояния должны совпадать с запущенной службой. Перезапуск только сетевого процесса ускорит подключение, если он уже ожидает backoff; SSH-сервер останавливать не нужно. Recovery сохраняет UUID, локальные учётки и данные.

Токену можно дать необязательное имя. Истёкшие join-токены удаляются после записи в аудит; API-токены автоматически отзываются. Истёкшие, отозванные и исчерпанные join-токены скрываются. Повторный запуск control plane не возобновляет старый bootstrap-токен.
